## 2026-11-19 复盘与改进

| 观察到的低效 | 改进 | 如何判断有效 |
| --- | --- | --- |
| 状态散落且互相过时 | 仅三份日志，状态只写进度，问题按 ID 更新 | 不再出现同一功能同时“未实现”和“已发布” |

| 构建等待期间重复查询和播报 | 保留一个运行，等待时整理文档或独立工作；约 45–60 秒查状态，完整日志结束后取一次 | 无重复触发/相互取消，更新只说明阶段变化或真实阻塞 |
| 为非致命警告改 codesign 导致回归 | 保持已验证命令；工具行为变更必须有对应平台证据 | 不为消除提示重建、删断言 |
| 发布最后才发现上传域名缺失 | 发布准备先核对实际附件上传主机和权限；校验通过的包直接复用 | 网络修复不重编译，不把空 Release 当附件完成 |
| 重复验证未受影响部分 | 按风险选择检查并记录覆盖 SHA；仅修改影响或新失败才重跑 | 不以“放心”为理由重复全量检查 |

这些是执行约定，尚未自动改造 CI 或证明耗时下降。后续按任务记录原生运行次数、重复运行原因、发现集成错误的阶段；有实际数据再评价收益，不增加每日统计负担。

## 产品设计工作方式 · 2026-11-19

执行[产品设计章程](product-spec.md)：兼任工程师与 UX/UI 设计师，主动优化体验，并保留用户对产品重要取舍的最终决定权。

每次功能开发先简短思考：用户为什么需要它、最自然的操作是什么、是否存在多余点击/菜单/确认、新用户能否看懂、高频动作是否随手可见、内容是否突出、是否符合全 App 交互语言。无需把全部思考写成报告。

较大界面功能开工前用 2–4 句说明：**具体问题 → 推荐方案 → 用户收益 → 成本或缺点**。例：“资料条目需要先进入管理页才能阅读；建议点击直接打开，长按管理、选择模式批量处理。减少阅读中断，需调整导航及保留选择状态。”这只是判断模板，不代表已检查或修改当前界面。

| 决策范围 | 执行方式 |
| --- | --- |
| 排版、视觉层级、常用按钮/工具栏/列表/卡片、减少无意义点击、明显违背既定规范的小问题 | 在当前任务内自主实现并针对性验证，无需逐项确认 |
| 重要页面或导航重规划、新交互模式、大范围设计系统变更、有依据的偏好替代建议 | 先给简短方案，再开展实现；明确建议与已决定事项，不把提案当既成事实 |
| 改变明确产品方向、删除功能、修改核心对象语义/关系、重大存储/删除/备份/迁移调整、新账户/服务器/付费依赖 | 必须获得用户同意后执行；已有明确授权不重复确认 |

较大页面开发先研究与任务相关的成熟模式，来源和采用理由简记在当次进度条目，不新增设计流水账。网络不可用时说明依据，继续可独立工作。坚持最小可用闭环、针对性验证和数据安全底线，不以审美追求无限规划，也不以“功能能运行”忽略明显交互问题。重要体验改动检查真实操作路径；视觉/真机未验必须单列。

## 一次任务的最短闭环

1. **定位：**核对分支、未提交改动和用户目标；读进度顶部、对应计划章节及相关问题 ID。默认 feature/safari-extension，保护用户改动。需求明确直接做，缺少会影响方向的信息才问。
2. **确定交付：**写一句用户可观察的闭环和必要验收；较大界面先按上节给简短设计判断。区分实现/自动检查/真机验收；非阻塞项记问题日志，不扩大本轮范围。
3. **实现：**沿用架构，只读改相关文件。复杂通用能力先查现有依赖/官方框架，再有限评估成熟开源，锁版本和许可证；先核对实际 API 再集成。
4. **验证：**按下表检查。保存失败原文和提交，不清数据、不删安全检查。相同错误两次修复仍无进展，停止重复尝试，记录阻塞并继续独立工作。
5. **稳定化：**闭环完成后集中可读性、重复计算/IO 检查；只优化有依据的热点，保持语义。发布候选冻结功能后跑完整原生流程，失败只修相关原因。
6. **交付：**核对最终代码与通过检查的 SHA；记录不一致原因（如仅文档差异）。按已有授权提交/推送/发布，不重复索要授权。报告实现、模块、已过检查、未验项及阻塞五项。

## 检查选择

| 改动 | 最小必要检查 |
| --- | --- |
| 日志/文档 | diff 空白、相对链接、引用与状态一致性；不构建 |
| Safari/协议逻辑 | 对应 Node 测试；协议改动同步 Swift Schema 资源与双方语义验证 |
| Swift 核心业务 | 受影响测试；包或跨模块集成变化再扩大 |
| SwiftUI/Readium/其他原生适配 | 锁版本 API 核对及真实 Xcode 编译；Linux parse 仅语法检查 |
| 持久化/删除/关系/迁移/备份恢复 | 重开、原件保留、引用完整、失败原子性/回滚；导入还要重复和 ID 重映射；恶意输入边界 |
| Native Messaging/App Groups/权限 | 持久后确认、同 ID 重试去重、损坏保留、配置失败显式报告；权限受影响时真机验收 |
| 发布候选 | 锁文件、核心及模拟器、arm64 iPhoneOS 归档、嵌入扩展、签名权限、ZIP/版本/SHA；真机结果另记 |

现有 ipados.yml 把模拟器测试和归档串联；不要声称已实现独立快速编译流水线。未来拆分/缓存仅在有明确收益时另开任务，不能削弱发布检查。

## 发布与故障处理

- 发布前核对版本、标签是否存在、上传/下载域名及授权；不要试探上传私密数据。使用已有候选和正常客户端验证实际服务。
- 同一候选只保留一个 CI 运行，不因慢启动取消。区分排队、编译、模拟器、打包、网络、GitHub 权限；只看失败层。
- IPA 本体摘要不同于外层 Artifact 摘要。保留 build SHA、分支 SHA、测试数量、版本、附件 URL/到期日；不能用旧包代替新包。
- 网络变更后确认当前生效策略再试，禁止绕过代理/TLS；权限没有变化时不反复请求同一失败操作。
- 只有完成实际检查才标通过；完整阶段真机验收未完成要明确。Release 公开和附件上传分别记录，缺附件时提供真实可用交付入口并标期限。
